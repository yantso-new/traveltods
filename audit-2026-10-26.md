# TravelTods — Product, Technical & Design Audit

_26 Oct 2026 · audited against `main` @ `09b2002`, live site www.traveltods.world, and the prod + dev Convex deployments (read-only)._

---

## 1. Verdict

TravelTods promises **data-driven family scores** for destinations. In production that data is almost entirely default constants. The site has 451 destination records. Almost all of them are the same placeholder page with a different city name. The visible scores don't separate one city from another, and about 108 of these placeholder pages carry a "Verified" tag.

On top of that:

- A rendering bug makes database-backed destination pages return a 500 (I tested Lisbon and Paris). Only the 6 hard-coded mock destinations render. Separately, the production backend is behind the frontend.
- Every write operation on the backend is public.
- The site has one waitlist signup ever (19 May 2026).

There are real assets to build on:

- **22 hand-written blog posts**, including 10 Iberia destination guides with real places and sources.
- A **reasonable design-token system**.
- A sound **Next.js + Convex** foundation.

The refactor below throws out the "auto-score every city on earth" idea. In its place it builds a small, deep, trustworthy family travel guide that earns money from bookings.

## 2. Evidence

### 2.1 The family score is not real data (prod, 451 rows)

| Metric | Most common value | Share of rows with that exact value |
|---|---|---|
| healthyFood | 100 | **100%** |
| costAffordability | 60 | **100%** |
| kidActivities | 60 | 96% |
| safety | 70 | 96% |
| playgrounds | 44 | 96% |
| sidewalks | 39 | 96% |
| accessibility | 60 | 96% |
| strollerFriendly | 60 | 95% |
| weatherComfort | 70 | 76% |

- Only 124 of 451 records have a family score at all. Of those, **98 fall between 61 and 64**. The score doesn't discriminate.
- **435 of 451** short descriptions read `Discover {City} in {Country}.` and 316 long descriptions are the template sentence. Prod Lisbon reads: _"Discover Lisbon, a destination in Portugal. Explore what this location has to offer for families and travelers."_ That page is tagged `Verified`.
- Root causes in code:
  - `convex/destinations.ts:592-603` hardcodes `parkCount: 5`, `averageRating: 4.0` and `strollerMentions: 50`.
  - `convex/lib/scores.ts` returns a fixed default whenever an API call fails, and many sub-scores are constants anyway: `markets = 0.3`, `keywords = 0.2`, `terrain = 0.8`, `transit = 0.8`, `restrooms = 0.7`.
  - The cost and safety-infrastructure integrations are failing silently. Cost is 60 on every row, and safety is 70 on 96% of rows.
- Even working data wouldn't make a good parent signal. Streetlight and police-station counts within 5 km are not "safety for toddlers". A healthy-restaurant ratio from OpenTripMap is not "healthy food".
- The dev deployment shows the same pattern (181 rows, healthyFood = 100 on all).
- The methodology page says nothing is labelled verified without a verification record. The `Verified` and `Data Reviewed` tags contradict that.

### 2.2 The live site is broken

| Route | Status |
|---|---|
| `/destination/Tokyo%2C%20Japan` (hard-coded mock) | 200 |
| `/destination/Lisbon%2C%20Portugal` (database record) | **500** |
| `/destination/Paris%2C%20France` (database record) | **500** |
| `/destination/Nowhere%2C%20Atlantis` (unknown) | **500**, should be 404 |

- **Cause of the 500s (reproduced with a local `next build && next start`):**
  - `app/destination/[id]/page.tsx` exports `generateStaticParams() { return [] }`, which makes the route static (ISR on demand).
  - Any non-mock ID then calls Convex `fetchQuery`. That fetch is uncached, which forces dynamic rendering, and Next throws _"Page changed from static to dynamic at runtime"_ → 500.
  - Mocks render because they never hit Convex.
  - The `try/catch` in `lib/published-destinations.ts` also swallows Next's `DYNAMIC_SERVER_USAGE` signal, which it must re-throw.
  - **Fix:** drop `generateStaticParams` (or set `dynamic = "force-dynamic"`), or generate the curated slugs at build time and serve from cache.
  - `pnpm dev` doesn't reproduce this, which is why it shipped.
- **Separate issue, deploy drift:** prod Convex is missing functions that the deployed Next.js code calls. `destinations:getPublishedDestinationInventory` → _"Could not find function"_. The frontend shipped without `npx convex deploy`, so the sitemap's try/catch falls back to the 6 hard-coded mocks.
- The sitemap also uses the bare `traveltods.world` host while the site serves `www.`.
- The homepage "Top Picks" grid is client-only (`app/page.tsx` is `"use client"`). It isn't in the server HTML. Search engines see a heading with an empty section, and in my headless capture the grid never filled.
- Material Symbols ligature names show up in the page text as `family_restroom`, `expand_more` and `menu`. That's what crawlers and some screen readers read.
- Blog images hotlink `unsplash.com/photos/{id}/download`, which is a 302 redirect. This breaks Unsplash's hotlinking and attribution rules and is fragile.

### 2.3 The backend is wide open (P0 security)

Prod exposes these **public** mutations and actions with no auth (the Convex URL ships in the JS bundle):

- `saveDestination`: anyone can overwrite any destination's content and images.
- `deleteDestinationsWithUnknownCountry`, `normalizeDestinationCasing`, `seedDestinations`, `patchSuggestions`, `updateDestinationImage`
- `refreshAllDestinations`, `refreshDestinationImages`, `populateNewFields`, `backfillCountryDestinations`, `testDestinationData`: anyone can burn every third-party API quota.
- Local code adds two more that aren't deployed yet: `patchNeighborhoods` and `repairInvalidNeighborhoods`. Build the lockdown from the local code, not the prod list.
- `gatherDestination` runs whenever anyone visits `/destination/<anything>`. It fires 11 API calls and can trigger a country backfill. That's how junk rows like _"Kampung Alor Madi, Malaysia"_, a lowercase _"lagos, Portugal"_ and a duplicate _"Tokyo"_ (dev) got in.

### 2.4 Traction & monetization

- 1 waitlist signup in prod, ever. The CTA is "Join Pioneers" in one place and "Join Community" in another, and it doesn't say what you're joining.
- Viator runs in production mode, but only 28 of 451 destinations have a Viator ID. Affiliate attribution on `productUrl` hasn't been verified, and nothing tracks outbound clicks.
- There are no hotel or accommodation links. Accommodation is the highest-value affiliate category in family travel.

### 2.5 Codebase hygiene

- Dead weight:
  - `legacy/` (an old Vite app)
  - 9 `scripts/debug-viator-*` and `test-viator*` files
  - `destinations.json` (1.2 MB), `known_destinations.txt`, `parse_destinations.py`
  - `tsconfig.tsbuildinfo`, which is committed
  - both `package-lock.json` and `pnpm-lock.yaml`
  - a public `/design-system` route
  - the stock create-next-app README
- The homepage merges `MOCK_DESTINATIONS` with database rows. The 6 mocks are the only destination pages that actually render, and their copy is hand-written marketing ("ranked safest city in 2026…") with no sources.
- Blog content lives in a 900-line `blogData.ts` string file. The posts are about 300 words but claim "6 min read".
- The site loads two icon systems: the Material Symbols webfont, which is render-blocking from Google Fonts, and lucide-react.
- There's no CI, no tests and no smoke check. A single Playwright check on `/destination/Lisbon…` would have caught the 500s.

## 3. Strategy: what TravelTods should be

### The decision

| | **A. Curated, data-backed family guide** (recommended) | **B. Fix the scoring engine** |
|---|---|---|
| Promise | "The most useful guide to travelling with under-5s in Europe" | "Score any city for families" |
| Pages | 30–50 deep destinations, each one a real piece of work | Hundreds of generated pages |
| Moat | Specific, checked, parent-useful detail | Little: the inputs are public OSM data anyone can query |
| SEO risk | Low: helpful-content friendly | High: thin programmatic pages are what Google demotes |
| Cost to make credible | Writing and research time | A new data pipeline, and the outputs still aren't trustworthy proxies |

**Recommendation: A.** Data stays in the product, but as evidence inside curated pages: month-by-month climate, playground counts near a recommended neighbourhood, hill and cobble warnings. It is not a headline 0–10 score. The 10 Iberia guides are already the seed. Start with **Portugal + Spain**, then expand along routes families from the UK, Germany and Israel actually fly.

### Who it's for

Parents of **0–5 year-olds** (extend to under-10 later) planning a short-haul trip. They need to know:

1. Will this be easy with a pram and naps?
2. When should we go?
3. Where should we stay?
4. What will the kids actually enjoy?
5. What's the plan B if it rains, or it's 38 °C?

Generic travel sites answer none of these well. That gap is the product.

## 4. Features that create value

Ranked by value ÷ effort.

1. **Destination guide v2 (the core page).** Each page has:
   - a Parent Verdict (3 lines)
   - an **age-band fit** (baby / toddler / preschool / 6–10) with a reason for each band
   - a **stroller verdict** (full-size OK / compact only / bring a carrier)
   - **When to go**, month by month, with heat, rain, school-holiday crowds and sea temperature. Open-Meteo is already integrated and is the one data source that partly works.
   - **Where to stay**: 2–3 neighbourhoods, each with a reason, plus specific family-ready hotels (affiliate)
   - **Top things to do**, each with an age range, stroller access, time needed and an indoor/outdoor flag
   - a **nap-friendly sample day**
   - a **rain / heat plan B**
   - **logistics**: car-seat rules, taxis with child seats, tap water, pharmacies, changing facilities, emergency number
   - **Sources & last checked** date per section
2. **Merge blog guides into destination pages.** Right now `/blog/lisbon-with-kids-under-10` and `/destination/Lisbon…` compete for the same query, and one of them is a 500. Keep one canonical page per place. The blog keeps only tips content (packing, jet lag, flights).
3. **Trip finder (homepage hero).** Departure city, kids' ages, month, trip type (beach / city / nature) and max flight time return a shortlist with reasons. Use filters over curated data; you don't need AI. This replaces a search box that currently creates junk rows.
4. **Collections**, for example:
   - "Easy first trip with a baby"
   - "Winter sun under 4h from London"
   - "Beach + city combos for toddlers"
   - "Car-free family breaks"

   These are high-intent SEO landing pages and cheap to build once the data model exists.
5. **Lead magnet + newsletter.** Replace the vague waitlist with something concrete: "Toddler packing checklist (printable) + monthly where-to-go-next email". Add a per-guide download: "Lisbon with a toddler, 1-page offline cheat-sheet".
6. **Save & compare shortlist.** Use localStorage first and add accounts later. Compare 2–3 places side by side on flight time, best month, stroller verdict and price level.
7. **Parent tips with verification (later moat).** Parents submit tips such as "Oceanário stroller parking is by the left entrance". You moderate them, and each tip shows a date and the child's age at the time of the visit.

**Drop:**

- the radar chart
- headline 0–10 scores built from proxies
- auto-gathering of arbitrary cities
- "Verified" and "Data Reviewed" tags
- the claim of "nap-friendliness filters", which don't exist

## 5. Technical plan

**Keep:** Next.js 16 (App Router), Convex, Tailwind 4, Vercel. The stack isn't the problem; how it's used is.

| Area | Change |
|---|---|
| **Security** | Convert every mutation and action except `waitlist.join` to `internalMutation` / `internalAction`. Run admin work via `npx convex run`, or an auth-gated `/admin` (Convex Auth or Clerk). Validate and rate-limit `waitlist.join`. Delete `test_data.ts`, `seed.ts` and the one-off repair mutations from prod. |
| **Deploys** | Set the Vercel build command to `npx convex deploy --cmd 'pnpm build'` so the frontend and backend ship together. Add GitHub Actions for typecheck, lint and build, plus a Playwright smoke test against `next start` (not `dev`, which hides the 500) on `/`, a destination, `/blog`, `/sitemap.xml` and a 404 route. |
| **Rendering** | Server-render and statically generate the homepage, destination, country and blog pages (`generateStaticParams` + ISR / `revalidateTag`). Use client islands only for the trip finder, save and filters. Unknown destinations call `notFound()` and are never gathered on request. |
| **URLs** | Use clean slugs: `/portugal/lisbon` instead of `/destination/Lisbon%2C%20Portugal`. Add 301s from old URLs. Canonicalise on `www`. |
| **Content** | Move editorial content out of `blogData.ts` into **MDX + Keystatic** (git-based, typed, free, works for a solo editor). Sanity is the alternative if non-technical writers join. Destination guides become structured content (fields for verdict, age bands, months, stays, activities, sources), not free text. |
| **Data model** | Use Convex for dynamic and enrichment data only: `places` (normalised POIs with source, coordinates, `lastVerified`), `climate` (monthly), `affiliateLinks`, `savedLists`, `tips`, `subscribers`. Every metric stores `{value, source, fetchedAt}`, never a silent default. If data is missing, the UI shows nothing. |
| **Pipeline** | Enrichment (climate, POIs, Viator) runs as cron or admin-triggered `internalAction`s with logging of failures, not on page view. Wipe or `noindex` the 451 template rows. Rebuild only curated destinations. |
| **Images** | Self-host via `next/image` + Vercel Blob or Convex storage. Use the Unsplash API properly (attribution + download endpoint), or better, your own and parent-submitted photos. Fix the broken `/download` hotlinks. |
| **Icons / fonts** | Drop the Material Symbols webfont (render-blocking, leaks ligature text) and standardise on lucide-react. Self-host fonts via `next/font`. |
| **Analytics** | Keep Vercel Analytics. Add PostHog for funnels: landing → guide → outbound affiliate click, trip-finder usage and newsletter conversion. Track every outbound click. |
| **Cleanup** | Delete `legacy/`, the debug and test scripts, `destinations.json`, `known_destinations.txt`, `parse_destinations.py`, `MOCK_DESTINATIONS` merging, the `/design-system` route in prod, and the committed `tsbuildinfo`. Pick one lockfile (pnpm). Write a real README. |

## 6. Design direction

**Today:** clean but generic. The look is a stock AI-photo hero family, `rounded-3xl` cards everywhere and Plus Jakarta Black headlines on every section. Nothing about it is ownable, and nothing signals "researched by parents". The hero copy promises features that don't exist.

**Direction: an editorial field guide.** Think Monocle or Cereal calm, crossed with a practical guidebook. Warm, confident, and dense with useful detail.

- **Typography:** use a characterful serif for headlines (Fraunces or Newsreader) and a neutral sans for UI and body text. Keep heavy weights for numbers and labels only. Today every heading is shouting.
- **Palette:** keep the coastal teal and sand tokens; they're good and already AA-checked. Add one warm terracotta accent for "heads-up" warnings (hills, heat, cobbles).
- **Signature components** (these become the brand):
  - **Parent Verdict** card
  - **Age-band strip**: 👶 baby ✓ · toddler ⚠ hills · 3–5 ✓✓ · 6–10 ✓✓
  - **Stroller verdict** icon set
  - **Month strip**: 12 cells coloured by family comfort, with tap-for-detail
  - **Nap-friendly day timeline**: morning anchor, lunch, nap window, afternoon play
  - **"Last checked" + sources** footer per section (visible trust)
- **Photography:** real, specific places at child eye-level (playgrounds, trams, aquariums), not stock families.
- **Information architecture:**
  - **Home:** trip finder → collections → featured guides → "how we research" → newsletter + checklist.
  - **Destination:** Verdict → ages → when to go → where to stay → things to do → sample day → plan B → logistics → sources.
- **Mobile-first:** parents plan on their phones during nap time. Keep a sticky "Save" and "Where to stay" bar, use bottom-sheet filters and make every page skimmable in 30 seconds.

## 7. How the site makes money

| Stream | Notes | When |
|---|---|---|
| Hotel / stay affiliate | Booking.com (via Awin), Expedia Group or Stay22 map embeds on "Where to stay". This is the biggest lever. | Phase 2 |
| Activities | Viator (already integrated, so verify attribution) + GetYourGuide | Phase 2 |
| Family-specific | Baby-gear rental (BabyQuip-style local services), car hire with child seats, family travel insurance | Phase 3 |
| Newsletter | Seasonal where-to-go issues. Sponsorships once you pass ~5k subscribers. | Phase 2+ |
| Paid printables | Detailed itineraries and offline guides (€5–9) | Later |

**KPIs:**

- indexed pages with impressions
- organic clicks to guides
- outbound affiliate CTR
- revenue per 1,000 sessions
- newsletter signups per week
